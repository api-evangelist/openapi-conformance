# OpenAPI Conformance

How the leading open-source [OpenAPI](https://spec.openapis.org/oas/latest.html) validators, parsers and linters judge
valid and invalid OpenAPI 3.0, 3.1 and 3.2 documents. Report: **https://openapi-conformance.apievangelist.com**

Each case is an OpenAPI document that is either valid or breaks exactly one rule. Every tool runs against every case
and is scored on one question: did it call the document valid or invalid, and was it right?

- **schema** cases are decided by the official OAI JSON Schema for that version.
- **semantic** cases break a rule that only the spec's prose states (unique `operationId`s, path parameters that
  match the template, `$ref`s that resolve, security requirements that name a declared scheme, unique tag names).
  No schema can catch these, so they separate a validator from a schema check.

Sibling suite: [arazzo-conformance](https://github.com/api-evangelist/arazzo-conformance).

## Cases

| Set | Where | Count |
|---|---|---|
| OAI schema tests, OpenAPI 3.1 and 3.2 | `cases/oai/<line>/{pass,fail}/` | 46 + 67, copied unmodified, pinned in `cases/oai/SOURCE` |
| API Evangelist cases, OpenAPI 3.0.4, 3.1.1, 3.2.0 | `cases/ae/<version>/` + `manifest.yml` | 34 + 36 + 43, generated by `scripts/build-ae-cases.py` |

The OAI publishes no schema tests for 3.0, so 3.0 is covered by the AE cases alone.

The AE cases are one valid base document per version plus one mutation each. The manifest records the rule, the spec
section, and whether the schema or only the prose decides it. Where the official schema and the prose disagree, the
prose wins and the case carries a `note` (today: the 3.0 schema does not enforce the component-key pattern).

## Reference

`scripts/schema-check.mjs` validates against the official schema the way the OAI's own test runner does
([OAI/build-infra](https://github.com/OAI/build-infra)): hyperjump, `schema-base.yaml`, with the OAS dialect and
meta-schema registered so Schema Objects are checked too. It gets every OAI pass/fail case right; ajv does not
(it mis-resolves the dialect's `$dynamicRef` and rejects valid documents), which is why it is not used here.

## Tools

`tools.yml` lists each tool, the command, and how to read its result. A tool's verdict is its exit code (0 = valid).
Patterns refine that: `error` marks a crash; `unsupported` marks a tool declining the document's OpenAPI version,
shown as "version not supported" and never counted as a pass or a fail (declining an *unreleased* version such as
`3.2.1` is the right answer and counts as invalid); `fetch_error` marks a tool that could not fetch an external `$ref`
(one OAI case points at a URL that 404s).

Linters (`role: lints`) are judged on error-severity results only. Spectral and vacuum run with the rulesets in
`rulesets/` (their recommended sets; vacuum with the two error-level style rules `info-description` and
`operation-operationId` turned off, since the spec makes both optional). Redocly runs its `spec` ruleset.

To add a tool, add an entry to `tools.yml` and run `scripts/run.py --only <id>`, which merges into the day's results.

## Running

```sh
bash scripts/install-tools.sh .tools            # latest release of every tool; JDK + .NET into .tools if not on PATH
.tools/py/bin/python scripts/build-ae-cases.py  # only after editing the cases
.tools/py/bin/python scripts/run.py --tools $PWD/.tools   # writes results/<date>.json and docs/data/latest.json
python3 scripts/summary.py                      # per-tool, per-version scores in the terminal
```

`.github/workflows/conformance.yml` does the same every day at 06:30 UTC on the latest release of every tool and
commits the results to `main`, which Pages serves. Run it by hand from the Actions tab.

## Not yet covered

- libopenapi directly (vacuum is built on it), oas-kit (3.0 only), Rust `oas3`.
- AE semantic cases for discriminator mappings, callbacks and `$self`-relative references.
